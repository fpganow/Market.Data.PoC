🟡⚪ 10. recv.time / parse.time: tick is 6.4 ns, the Register read stays, decide the latch
   REWRITTEN 2026-10-11 22:00 after exporting poc.ip.kria.vi to AIXML (which shows which Timed
   Loop each node is in) and measuring the counter in the 19:37 netlist sim. The earlier text
   of this item (parser `time` "should be wired from the counter wire", "10 ns ticks") was
   wrong on two points; corrected facts:
   FACT 1  The tick counter (Feedback Node -> Increment -> Select, t = 0, s = ip.reset rising
           edge, f = x+1) is in the 156.25 MHz "PoC IP" Timed Loop, next to TDATA/TVALID/
           ip.reset (the wrapper marks those "sync to Clk40MhzDerived168x43B56_28MHz"). Sim:
           recv.time advances exactly 1 count per input beat (frame spacing / (beats + 64 idle)
           = 1.00 for all 19 gaps). ONE TICK = 6.4 ns, not 10 ns. Every latency figure
           published so far with 10 ns/tick is 1.56x too large (e.g. "first message 20-140 ns"
           is really 13-90 ns). decode_capture.py and eval_sim.py now use 6.4 (done here).
   FACT 2  bats.parser.vi is in the other Timed Loop (100 MHz, with the CMD/DEBUG outputs).
           The counter reaches it through a Register (written every cycle in the 156 MHz loop,
           read in the 100 MHz loop) - that Register IS the clock-domain crossing. A wire
           between two Timed Loops is impossible, so the Register read on the parser's `time`
           input STAYS. Its lag (1-3 ticks = 6-19 ns, phase dependent) is the price of the
           crossing: parse.time is always a few ticks LATE, never early. Sim 19:37 export:
           parse.time - recv.time = 1..80 ticks, never negative. Nothing to change.
   FACT 3  recv.time today = the counter value in the cycle the word was written into the CDC
           FIFO (per-word stamp); a CMD record therefore carries the arrival tick of the word
           that COMPLETED its message. The frame-start latch (recv.time = tick of the frame's
           first word) was removed on 2026-10-11 01:20.
   DECIDE  (the only remaining choice; both are legitimate)
     A. Frame-start latch (RECOMMENDED): parse.time - recv.time = time since the first byte of
        the packet arrived - what a trading system quotes, comparable with the earlier runs,
        and the host tools can group a frame by equal recv.time. Diagram change: the latch
        shown in fpga/poc.ip.kria.generated.vi (below).
     B. Per-word stamp (keep as is): parse.time - recv.time = the parser's own per-message
        latency (1 tick for a message completed by the arriving word, more for the ones queued
        behind it in the same frame). No diagram change; tell Claude and the host tools switch
        to grouping by sequence number (eval_sim.py already groups by pcap frame).

⚪⚪ 8. Known edge case, decide later (no fix yet): the eof clear in Read.Msg (buffer.length >=
   message length frame) also fires when two 6-byte messages end a frame and the parser is
   one message behind, dropping the last one. Only consecutive Time/End-of-Session/Unit-
   Clear messages at a frame end are affected. A clear on `done` alone (count reached)
   avoids it but leaves junk after a malformed frame; item 3's VI makes a clear-on-done
   safe again as long as items 5/6 clear on eof in the other two frames.
