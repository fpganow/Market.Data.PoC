🟢🟢 3. Preserve remainders longer than 8 bytes (orderId corruption 'OR\0D0204')   -- SIM OK 2026-10-11, remove
   WHERE   submodules/Market.Data.Bats.Parser/fpga/compress.buffer.vi, called twice from
           bats.parser.vi: in Read.Sequenced.Unit.Header (start.idx = 8, after the header is
           parsed) and in Read.Msg (start.idx = message length, after a message is emitted).
   NOW     The VI moves the bytes after the consumed message to the top of buffer.out, but
           it rebuilds buffer.out[0] ONLY. On the diagram: the Case Structure on
           Equal To 0?(Remainder.idx) has one Replace Array Subset per frame, both writing
           index 0 of the 9-element zero constant. The unaligned (False) frame also sizes
           its second-word mask with Remainder.len (= buffer.length AND 7), which assumes
           buffer[Word+1] is the last word of the buffer. (Remainder.idx, Word and
           Remainder.len are the three indicators on the front panel: start.idx AND 7,
           start.idx >> 3 and buffer.length AND 7.)
           Both assumptions hold while the remainder is < 8 bytes, which is the normal case
           (one 8-byte word added per cycle, one message consumed per cycle). They break
           when a message was ALREADY complete before this cycle's word was added: the
           parser is one message behind, the remainder is 9..15 bytes, and bytes 8.. of it
           are dropped (buffer.out[1] stays 0). Trigger: a 6-byte message (Time, End of
           Session, Unit Clear) following a 6- or 7-byte leftover. Observed once per test
           pcap (multi frame 9 msg 24, repro msg 93): OrderExecuted orderId 'OR\0D0204'.
           The bit-exact model reproduces it: ip_export/netlist_sim/compress_fix_proto.py.
   READY   compress.buffer.generated.vi (LabVIEW 2020 file, same connector pane 4815:
           buffer 11, buffer.length 10, start.idx 9 -> buffer.out 3, buffer.length.out 2)
           is in the same directory, in the repo clone and in the OneDrive tree. Built
           2026-10-07 from tools/labview-aixml/gen_compress_buffer_vi.py (AIXML in
           compress.buffer.xml) and verified: 79 vectors run in LabVIEW 2026 and the
           pcap case re-run in LabVIEW 2020 all match the model, which decodes both pcaps
           with 0 content mismatches (the old function: 1 each).
           What it computes, in the names used on its diagram (free labels explain each
           block):
             diff   = buffer.length - start.idx          -> buffer.length.out (unchanged)
             s      = start.idx AND 7                    (Remainder.idx)
             widx   = start.idx >> 3                     (Word)
             w0..w3 = Index Array(buffer, widx) with 4 outputs (past the end reads 0)
             Case on Equal To 0?(s):
               True  (aligned):  raw_k = w_k                              k = 0, 1, 2
               False:            raw_k = (w_k << 8s) OR (w_k+1 >> 8(8-s))  k = 0, 1, 2
                                 = the two Logical Shifts the old VI did for w0/w1,
                                   repeated for w1/w2 and w2/w3
             mask_k (outside the case, per word): Select chain on diff
               diff >= 8(k+1) -> all ones         (whole word valid)
               diff <= 8k     -> 0                (nothing left for this word)
               otherwise      -> all ones << 8*(8(k+1)-diff)   (top diff-8k bytes)
             buffer.out[k] = raw_k AND mask_k, written with three Replace Array Subset
             (index 0, 1, 2) into the 9-element zero constant.
           No shift amount ever reaches 64, so it does not depend on how Logical Shift
           saturates. The masks also stop stale bytes beyond buffer.length from leaking
           (they exist since the eof clear sets buffer.length to 0 without zeroing the
           words); the old VI leaked them when diff was 0 or 1 in the unaligned frame.
