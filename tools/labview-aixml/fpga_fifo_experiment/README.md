# FPGA FIFO by script — the one-FIFO experiment (2026-10-16)

**Result: a real LabVIEW FPGA FIFO (target-scoped, U64, 1024 elements) and its FIFO Method
Node were created by script in LabVIEW 2020 32-bit, inside the project's FPGA target
context, with no hand editing.** Evidence in this folder:

- `fifo_scratch.result.diagram.png` — LabVIEW's own print of the scratch VI's block diagram
  after the run: the `EXP-Fifo` Write node (Element / Timeout / Timed Out?) above the
  original `in -> +1 -> out`.
- `fifo_scratch.result.vi` — the scratch VI after the run (LabVIEW 2020 file; lvkit sees a
  `FIFO Method Node`, VI Server reports the node's class as `niFpgaContainer` at (100,100)).
- `EXP-Fifo.lvproj-item.xml` — the `<Item Name="EXP-Fifo" Type="FPGA FIFO">` LabVIEW wrote
  into the scratch copy of `Market.Data.PoC.lvproj` under `FPGA Target` (U64 type descriptor,
  Target-Scoped, requested 1024 / actual 1029, Block Memory, arbitrate-if-multiple).

Nothing in the real project was touched: everything ran against a scratch copy of the
LabVIEW tree under `C:\work\fpganow\lvgen\exp\tree\` (deleted afterwards).

## The API

NI's internal, unsupported FPGA scripting VIs, shipped with the FPGA Module in both
LabVIEW 2020 and 2026 here:
`<LabVIEW>\vi.lib\rvi\ClientSDK\Core\Script\Fifo\ProjectItem\{Public,Private}\nirviPiFifo_*.vi`
(password-locked, callable) and `<LabVIEW>\vi.lib\rvi\FIFO\Fifo_Common\nirvififoDropXNodeFromProject.vi`.
Sibling folders `Memory`, `Clocks`, `Container`, `Clip` have the same shape for memories,
clocks, registers/containers and CLIPs. NI does not support this API (forums.ni.com
td-p/3989913, an NI engineer pointing a user at it in 2019).

Call sequence used by `fifo_experiment.xml` (the helper VI, runs on My Computer):

1. `{LV.Application}` `Project.Open` (path) -> `{LV.Project}` `Root` ->
   `{LV.ProjectItem}` `Get All Descendents`; read `Name` of each and `Search 1D Array` for
   the target item ("FPGA Target") and the VI item ("fifo_scratch.vi").
2. `{LV.ProjectItem}` `VI Reference` of the VI item = the VI loaded **in the target
   context**; `{LV.VI}` `Block Diagram`.
3. `nirviPiFifo_CreateGlobalItem.vi (parent item = target item, name)` -> state cluster
   `nirviPiFifo_SetDataType2.vi (Data Type = To Variant(U64 0))`
   `nirviPiFifo_SetSize.vi (Size U32)`
   `nirviPiFifo_SetTransferType2.vi (Transfer Type = Target-Scoped; enum
    {Target-Scoped, Host to Target - DMA, Target to Host - DMA, Peer to Peer Reader/Writer})`
   `nirviPiFifo_CommitGlobal.vi` -> `ProjectItem` (the new FIFO item).
4. `nirvififoDropXNodeFromProject.vi (Scratch Diagram = the VI's block diagram,
   Fifo ProjectItem, X, Y)` -> `Succeeded` = TRUE: the FIFO Method Node (default method
   Write) is on the diagram.
5. `{LV.VI}` `Save.Instrument`, `{LV.Project}` `Save`, `Close`.

The whole run took 2.6 s in LabVIEW 2020 (353 project items scanned).

## How it was driven

- The helper VI was authored as AIXML, generated by the Zuehlke labview-mcp plugin in
  LabVIEW 2026 (`lvai_open_file` the six `nirvi*` VIs first so the `Call`s resolve by
  name; `lvai_vi_terminals` gave the exact terminal names), `SaveForPrevious(..., "20.0")`
  over 64-bit COM (`save2020_helper.ps1`), then run in LabVIEW 2020 32-bit over COM from
  the 32-bit PowerShell (`lv2020_run_helper.ps1`: `GetVIReference`, `SetControlValue` for
  the string/U32 controls, `Run`, `GetControlValue`). The vi.lib links are symbolic, so the
  2020 copy resolves to 2020's own `nirvi*` VIs.
- `print_bd.xml` / `lv2020_print_bd.ps1`: prints an FPGA-target VI's diagram to PNG through
  `{LV.VI}` `Print.VI To HTML` (Format = Complete) from inside the target context — the way
  to *see* a target VI from here. `open_bd3.xml` lists every diagram object's class and
  position (`{LV.Diagram}` `All Objects[]`, `{LV.GObject}` `Class Name`, `Position:Left/Top`)
  and runs `{LV.TopLevelDiagram}` `CleanUp`.

## Pitfalls met

- A `Property Node` whose `error out` is unwired pops LabVIEW's automatic error dialog on
  the first invalid reference (some descendants of `Get All Descendents` answer Error 1055
  on `Name`), and the dialog blocks the COM `Run` forever with nothing visible from WSL.
  Wire every error out (into an indexed tunnel is enough). `PrintWindow` on the dialog's
  hwnd + `PostMessage WM_CLOSE` recovered the session.
- Refs opened by a helper are released when it finishes, which closes the project and any
  window it opened: hold the helper with `Wait (ms)` (terminal `milliseconds to wait`) when a
  window must stay open, or print to PNG instead.
- The scratch VI is **broken (exec state 0)** after the drop: the Write node's `Element`
  input is unwired. Wiring it is the next step (`{LV.Node}` `Terminals[]` + `Connect Wire`,
  or `pylv`); the node itself is complete and the project item is valid.
- LabVIEW 2026 x64 has no USRP-X410 target support, so the helper must run in 2020.
